# AI 디자인 상담: 단계별 개발

2026-10-18. 사용자가 승인한 흐름: 취향 전달 → 해석한 조건 확인 → 추천 생성 → 추천안 선택 상담.
기존의 개별 가구 조작 AI 피드백 입력창과 작업실 연결은 사용자 요청으로 제거했다. 배치 검증과 자동 저장은 유지한다. 새 상담은 작업실의 별도 `AI 디자인 상담` 메뉴에서 시작한다. 기존 서버 피드백 API와 공간 검증 모듈은 이 UI 제거 범위에서 변경하지 않는다.

## 1단계 — 취향 입력과 입력 내용 확인 (완료)

- 생활 설명과 참고 사진을 함께 또는 각각 입력한다. 설명은 최대 2,000자.
- 파일 선택 및 상담 영역 안의 클립보드 이미지 붙여넣기로 첨부한다. 일반 텍스트 붙여넣기는 textarea의 기본 동작을 보존한다.
- JPG/PNG/WebP, 최대 3장, 장당 5 MiB, 디코딩 후 2,500만 화소 이하. 전체 배치를 검사하고 하나라도 잘못되면 이번 배치 전체를 거절하며 기존 사진은 보존한다.
- MIME와 파일 시그니처, 브라우저 이미지 디코딩을 확인한다. HTML/이미지 URL을 붙여넣어 외부 주소를 가져오지는 않는다.
- 미리보기, 개별 삭제, 입력 검토 및 수정. 검토는 원본 입력의 확인이며 AI의 해석 결과로 표시하지 않는다.
- 작업실 컴포넌트의 메모리에만 유지한다. 메뉴 전환/패널 닫기는 보존, 방 교체/작업실 이탈/새로고침은 초기화한다. 이미지 URL은 삭제·이탈·실패·비동기 취소 시 해제한다. 방 자동 저장 데이터에 이미지나 설명을 섞지 않는다.
- 1단계에서는 원문 검토만 제공했다. 2단계부터 아래 분석 API로 연결하며, 현재 배치 변경과 상담 기반 추천 생성은 여전히 없다.

검토 지점: 이미지와 설명 입력 흐름, 첨부 방법, 분량·용량 제한, 기존 작업실에서의 접근성.

## 2단계 — AI 해석과 조건 확인 (완료, 운영 실호출 확인)

- `POST /api/design-consultation/analyze` multipart 요청. `brief` JSON은 revision, description(최대 2,000자), 현재 가구 id/name/type(최대 24개)만 포함한다. `images`는 선택이며 최대 3장. 방/배치 저장 API를 호출하지 않는다.
- 브라우저에서 사진을 최대 1,024px, 장당 256 KiB 이하 JPEG로 변환하여 전송한다. 원본 미리보기는 유지한다. 캔버스 재인코딩으로 EXIF/파일명은 모델에 전달하지 않는다. WebP 첨부도 전송 전에 JPEG로 변환한다.
- 서버는 파일 수·5 MiB 제한·MIME·실제 이미지 형식·디코딩·2,500만 화소 제한을 재검증한다. 해상도를 먼저 읽고 subsampling한 뒤 JPEG 재인코딩한다. Spring multipart 전체 16 MiB, 개별 5 MiB 제한. 임시 multipart 파일은 프레임워크 요청 수명으로 관리하며 DB/상품/별도 영구 파일을 저장하지 않는다.
- 기존 OpenAI 호환 Chat Completions 클라이언트와 `ROOMFIT_LLM_FEEDBACK_ENABLED`, `ROOMFIT_LLM_FEEDBACK_API_KEY/BASE_URL/MODEL/TIMEOUT_MS`를 재사용한다. 상담 타임아웃은 25~60초, 브라우저는 70초다. 키는 서버 환경변수에만 둔다. root 설정 fallback은 기존 정책 그대로다.
- strict JSON schema로 summary, requirements, questions를 반환한다. 조건은 최대 12개, 질문은 최대 4개. 필드·enum·길이·원문 인용·실제 사진 번호·제공된 가구 ID를 서버와 클라이언트에서 확인한다. 실패 시 규칙/샘플 결과로 대체하지 않는다.
- 필수 여부는 REQUIRED/PREFERRED로 구분한다. 사진·추정은 사용자 확인 전 항상 PREFERRED다. 조건별 ‘꼭 지키기’ 체크로 사용자가 필수 여부를 바꿀 수 있다.
- 조건 출처: USER_TEXT(원문 부분 인용), REFERENCE_IMAGE(실제 제공된 1-based 사진 번호와 시각 근거), INFERENCE(추정 근거). 이미지에서 기존 가구 ID나 유지 의사를 추정하지 않는다. 텍스트의 명시 조건이 시각적 선호보다 우선한다.
- 대응 가능한 kind/value는 PURPOSE(휴식/업무/취미/수납), STYLE, PALETTE, KEEP_FURNITURE다. 대응 항목이 있으면 SUPPORTED, 상세 재질·활동 공간 등은 OTHER/NEEDS_ENGINE_SUPPORT, 중복 목적·상충 선택 또는 대상 불명확은 NEEDS_CLARIFICATION으로 보존한다. 이는 현재 추천 적용 여부나 동선 보장을 뜻하지 않는다.
- ‘요가 공간’, ‘모니터 2대’, 수치·금지 조건을 일반 목적 하나로 축소하지 않도록 프롬프트에 명시했다. 다만 실제 모델의 의미 해석 품질은 실 호출 평가가 필요하다.
- 결과에서 조건별 포함/제외, 내용 수정, 확인 완료/재수정이 가능하다. 수정한 문장은 기존 enum/가구 ID 매핑을 제거해 USER_EDIT/OTHER/NEEDS_REVIEW로 보존한다. 3단계에서 재해석 또는 명시적 매핑 검증 전에는 이 조건을 실행할 수 없다. 빈 내용이나 선택 조건 0개는 확인할 수 없다.
- 질문은 원문 설명에 답변을 추가한 뒤 재분석한다. 전체 채팅 이력을 보내는 챗봇은 이번 범위가 아니다.
- 입력 변경·방 편집·취소·이탈 시 요청을 중단하고 revision/방 snapshot/client scope가 달라진 결과를 버린다. 취소가 이미 전송된 서버/제공자 계산을 되돌린다는 의미는 아니다.
- 실패/미설정/취소 시 원본 사진과 설명을 유지한다. 미설정 503, 제공자/파싱 실패 502, 호출 제한 429, 잘못된 사진 400, 업로드 초과 413. 서버는 프로세스당 동시 2개/분당 20회로 호출을 제한한다. 로그는 requestId·stage·예외 종류·제공자 상태/요청 ID만 포함하며 본문·사진·키를 남기지 않는다.
- 현재 배치/기존 추천 설정/저장 상태는 수정하지 않는다. 확인한 조건은 작업실 메모리에만 남고 새로고침·이탈 시 사라진다. 기존 수동 추천은 별도로 동작한다.

검증: 서버 단위/HTTP 계약 테스트와 브라우저 검증. 2026-10-18 운영에서 기존 gpt-6-luna 설정으로 설명만·사진만·사진+설명 세 요청의 실제 OpenAI 응답(HTTP 200)을 확인했다. 상세 증거는 워크스페이스 루트 `docs/ui-tooling/qa/design-consultation-live-2026-10-18/`에 있다. 세 표본이 모든 입력의 의미 해석 정확성을 보장하지는 않는다.

공식 규격: [이미지 입력](https://developers.openai.com/api/docs/guides/images-vision), [구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat). 기존 클라이언트와의 호환을 위해 Chat Completions를 확장했고 전체 API 마이그레이션은 하지 않았다.

## 3단계 — 확인한 조건으로 추천 생성 (구현)

- 사용자에게 의미가 없는 SUPPORTED/NEEDS_ENGINE_SUPPORT 배지와 개발 상태 설명을 화면에서 제거했다. 2단계 응답 필드는 이전 클라이언트와의 호환을 위해 유지한다.
- 조건 확인 뒤 ‘이 조건으로 추천 생성’ 버튼이 나타난다. `POST /api/design-consultation/prepare`는 확인한 조건의 id/현재 문장/필수 여부, 현재 가구 id/name/type을 JSON으로 보낸다. 원본 이미지·과거 전체 대화는 재전송하지 않는다. 수정한 문장도 이전 enum을 재사용하지 않고 새로 해석한다.
- 서버는 기존 서버 전용 키/모델/타임아웃 및 동시 2개·분당 20회 제한을 재사용한다. 조건 최대 12개·각 300자·가구 최대 24개, 조건 ID는 중복 없이 모두 응답에 포함되어야 한다.
- 결과는 조건별 effects/unresolved다. PURPOSE, STYLE, PALETTE, REQUIRE_TYPE(종류별 총 개수 1–24), EXCLUDE_TYPE(해당 종류 전부 제외), KEEP_ITEM(실제 현재 가구 ID)만 허용한다. 임의 좌표·상품·크기를 모델이 만들지 않는다. KEEP_ITEM은 상품·치수·위치·방향을 유지한다.
- 숫자가 없는 단수 가구 요청은 1개다. ‘식물이 많은’ 같은 수량 표현은 임의 개수로 바꾸지 않고 구체적인 수량을 질문하도록 명시했다. 활동 공간 크기·재질·특정 방향 등 아직 측정/실행할 수 없는 내용은 unresolved로 보존한다. ‘따뜻한 색감’은 베이지로 해석 가능하지만 ‘따뜻한 분위기’ 전체(조명/재질 등)가 구현됐다고 주장하지 않는다.
- 클라이언트도 응답 ID/효과/enum/수량/현재 가구 ID를 검증한다. 서로 다른 목적·스타일·색감, 서로 다른 수량, 포함·제외 충돌, 고정 가구와 제외 충돌은 임의 선택 없이 추천을 중단하고 이유를 표시한다. 기존 엔진은 한 목적·스타일·색감만 받으므로 여러 개를 동시에 선택한 조건은 구체화가 필요하다.
- unresolved가 있는 필수 조건은 추천을 막는다. 선호 조건은 그 조건의 일부 효과까지 함께 제외하며 ‘이번 추천에서 반영하지 않은 요청’에 이유를 표시한다. 부분 해석을 전체 이행이라고 표시하지 않는다. 반영할 수 있는 조건이 하나도 없으면 추천하지 않는다.
- 미지정 목적/스타일/색감은 휴식/내추럴/자동 색 조합 기본값이다. 추천 기준을 화면에 표시한다. 새 디자인을 기준으로 구성하되 사용자가 유지한 가구 및 기존 자물쇠 고정은 지킨다. 현재 배치/가구 전체 보존은 명시한 조건에 따르며 수동 추천 설정을 덮어쓰지 않는다.
- 엔진은 기존 가구 선택·다양성·공간 검증을 재사용한다. 종류별 총 개수는 기본/선택 슬롯에 우선하며 필수 슬롯으로 생성한다. 제외 종류는 기본/선택 슬롯에서 제거한다. 마지막 후보 검증에서도 개수·제외·필수 스타일을 다시 확인한다. 책상 제외는 책상 일체형 로프트 침대에도 적용한다. 모니터·TV 같은 가구는 실제 받침 가구가 필요하며 받침 제외와 충돌하면 추천하지 않는다.
- 확인한 조건이 계산 가능한 상태라는 이유만으로 공간에 배치가 가능하다고 보장하지 않는다. 조건을 만족하는 배치를 못 찾으면 현재 배치를 유지하고 기존 엔진의 실패 안내를 표시한다.
- 결과는 상담 메뉴와 수동 추천 메뉴에서 기존 추천안 비교 UI를 재사용한다. 미리보기는 저장하지 않고 ‘이 추천안 적용’에서만 현재 배치를 바꾸고 자동 저장한다. 조건/방 변경, 취소, 이탈 시 준비 요청과 worker를 중단하고 늦은 결과를 버린다.

검증: JUnit 준비 변환기/HTTP 계약/공통 클라이언트, Vitest 컴파일러·엔진·기존 웹 전체 검사, PC 1440×900 및 모바일 390×844 브라우저 검증. 브라우저는 AI 응답만 mock하고 실제 worker를 사용했다. 실제 운영 방을 수정하지 않았다. 구현 시점의 검증은 로컬이며, 배포·실호출 결과는 별도 QA 기록으로 구분한다. 상세 증거: 루트 `docs/ui-tooling/qa/design-consultation-stage3-2026-10-18/`.

검토 지점: 필수 조건 이행, 가구 매칭, 유지/제외 충돌, 후보 다양성과 공간 검증. 자유로운 재질·수치 공간·복수 목적/색 조합의 구조화는 이후 확장 대상이다.

## 4단계 — 선택 상담

생활 요구와 추천안의 측정 결과를 연결해 장단점과 선택 이유를 설명한다. 엔진의 측정 수치/한계와 미적 의견을 구분한다. 추정 채광을 실제 일조량처럼, 추정 수납을 실제 수납 용량처럼 말하지 않는다. 구체적 비교에 필요한 근거를 엔진에서 제공하고 LLM이 없는 수치를 만들지 못하게 한다.

검토 지점: 근거에 맞는 설명, 후속 질문 맥락, 마음에 드는 안을 찾는 시간과 적용 후 수정 부담.

## 해석 재사용·원룸 기본값·추천 결과 확인 (2026-10-18, 로컬 검증)

- 웹은 analyze에 `recommendationReady:true`를 보낸다. 서버가 조건 문장과 조건별 effects/unresolved를 한 번에 반환한다. 사용자가 확인한 문장과 실행 의미를 그대로 재사용하므로, 내용 수정 없는 확인·포함 여부·필수 여부 변경·재생성에는 prepare 호출이 없다. 구형 서버 응답에 preparation이 없으면 기존 prepare 경로를 사용한다.
- 조건 내용을 수정하면 선택된 수정 조건만 prepare로 보낸다. 다른 조건의 해석은 유지한다. 분석/준비 결과는 작업실 메모리에만 존재하며 방·원문·사진 변경과 취소/오래된 응답의 처리 규칙은 유지한다.
- 독립된 뜻별로 조건을 나눈다. 예시 원문은 공부 목적, 화분 수량, 내추럴 스타일, 책상, 책장, 옷장 제외로 해석한다. 같은 canonical effects를 완전히 표현한 중복 조건은 서버에서 합치며 미지원 상세 요구를 버리지 않는다.
- 원룸 제안값: 식물이 ‘많은/풍성한’=총 3개, ‘여러/몇 개’=총 2개, ‘조금/약간’=총 1개. 따뜻한 분위기는 내추럴 스타일, 따뜻한 색감은 베이지로 제안한다. 추정은 PREFERRED/INFERENCE이고 확인 화면 설명에 제안임을 밝힌다. 명시 수량·스타일·색·제외를 우선한다. 실제 조명·온도·특정 재질 변경을 약속하지 않는다. 사용자가 실제로 요청한 미지원 수치/상세 요구는 계속 보존한다.
- 추천 표시 전과 적용 직전에 별도 검증기가 카탈로그의 productId/variantId를 대조하고 실제 가구 종류·총 수량·제외·유지·필수 스타일·적용 색감을 검사한다. 실패한 후보는 보여주거나 적용하지 않는다. 기존 공간/개폐/통로 검증과 함께 사용하며 LLM을 추가 호출하지 않는다.
- 각 추천의 ‘가구 구성·조건 확인’에서 실제 종류·상품명·개수와 요청/결과 수량을 볼 수 있다. 흰 유리문 가구도 ‘책장 / 오픈 선반 · 클래식 유리도어 책장’으로 식별된다.

검증: 웹 84파일/774테스트, 빌드·lint. 브라우저는 제공자 응답만 고정하고 실제 Worker로 화분3/책상1/책장1/옷장0 후보3개, 수정 조건만 재호출, 재생성·포함 토글 시 캐시 재사용, 누락 후보 차단, PC1440×900·모바일390×844·키보드 조작을 확인했다. 새 프롬프트의 실제 운영 OpenAI 해석·종단 응답 시간은 배포 후 별도 검증해야 한다. 로컬 935ms 측정은 고정 응답 이후 추천 계산 시간이며 운영 AI 응답 속도 개선 수치로 사용하지 않는다.

## 상담 화면과 원룸 표현 해석 개선 (2026-10-18, 로컬 검증)

- 상단 진행 순서는 화살표로 연결하고, 취향 입력→조건 확인→추천·비교 중 현재 단계를 표시한다. 확인을 완료하면 추천 단계로, 필수 조건 때문에 차단되면 조건 확인 단계로 표시한다.
- ‘더 확인하고 싶은 점’을 ‘조건을 더 구체화해 주세요’로 바꾸고, 조건 목록 앞의 강조 영역으로 옮겼다. 연결된 미해결 조건은 ‘해당 조건 수정’으로 바로 이동하고, 질문만 있는 결과는 ‘설명 보완하기’로 원문을 유지한 채 입력 화면으로 돌아간다. 추천 준비에서 해결된 질문은 다시 보여주지 않는다.
- 상담 텍스트 입력은 데스크톱14px/400으로 낮췄다. 모바일에서는 입력 시 확대 방지를 위해16px를 유지하고 굵기는400으로 통일한다. 질문 제목16px·본문14px, 기존 중립 색상·선형 아이콘·공통 버튼을 재사용한다. 안내·업로드 오류·조건 검증 메시지는 ‘습니다’체로 정리했다.
- 원룸 수량 제안은 화분 이외의 모든 지원 가구로 확장했다. 종류를 명시한 ‘많은/풍성한/넉넉한’은 화분3개, 그 외 종류2개를 제안한다(소파2/책장2/의자2 등). ‘여러/몇 개’는2개, ‘적은/조금/최소한’은1개다. 숫자가 있으면 그 숫자를, 제외를 말하면 제외를 우선한다. 추정은 원룸 기준 제안으로 표시하고 실제 수용 가능성은 엔진이 검사한다.
- ‘옷/책이 많다’는 소지품·수납량 선호이므로 가구 수를 바로 늘리지 않고 수납 목적과 구분한다. 종류 없는 ‘가구가 적은’은 미니멀 스타일 제안으로 설명하고 실제 총 개수 감소를 보장하지 않는다. 대상·의도·서로 충돌한 명시 조건이 모호할 때의 확인 질문은 유지한다.

검증: 웹85파일779테스트·build·lint, 서버 상담26테스트·bootJar 통과. 브라우저 검증은 AI 응답만 고정하고 실제 Worker를 사용했다. 새 형용사 해석 지침의 실제 OpenAI 응답은 배포 후 별도 검증이 필요하다. 이번 수정은 push·배포하지 않았다.
